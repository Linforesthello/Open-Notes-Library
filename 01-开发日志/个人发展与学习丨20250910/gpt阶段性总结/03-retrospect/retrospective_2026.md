**关键转折月**。下位机整合：代码重构、PID 模块化、CAN 通信首次打通。月底时"外部串口 → 网关 → CAN 网络 → 电机控制"全链路跑通。

**但月初病了一周**（11-25 到 12-01）。

### 逐日

**11-25 → 12-01（病愈）**
"病了好几天"回来看代码。开始着手"OMF_UARTback"代码库优化。意识到现有代码"一坨屎山，不改没法继续加功能"。

**12-02 ~ 12-04**
开始解耦 FreeRTOS 任务。把 motor control、encoder、logger、command 拆成独立 task。建立 task_motor.c / motor.c / encoder_task.c / logger_task.c / command.c / command_task.c。

**12-05**
**重大发现：之前用 TB6612 驱动芯片去控无刷电机，是错误操作**。A 口烧了，换 B 口才勉强控制。**"选型要先看芯片支持的电机类型"**——交了学费。

**12-06 ~ 12-08**
代码架构大改。motor.c 和 motor_task.c 解耦。思考"for(;;) 到底该出现在哪里"——FreeRTOS 任务结构的理解加深。

**12-08**
仅 3 行。记录队友 "杨zy git 记录"。

**12-09 ~ 12-10**
深度优化。**重构 4 大任务**：
- **command.c**：协议解析
- **uart_app.c**：串口收发
- **encoder_task.c**：编码器读取
- **logger_task.c**：调试打印
**同时踩了 PWM 频率的坑**：之前为了调无刷电机把频率改到 20kHz，换回直流电机后电机不动→查出来是频率不匹配→改回 1kHz 解决。**"不同电机类型对 PWM 频率要求不同"**。

**12-13**
代码基本迁移完毕。遗留问题：
1. 速度映射只有 -50~0~50，不是 -1000~0~1000
2. 基础驱动代码仍然不够优化
3. **代码仍然是黑箱**——串口输入命令后没有串口反馈
4. **无统一数据栈**供上位机读取

**12-14 ~ 12-17（1217-1218）**
**队列冲突 Bug**。FreeRTOS 队列冲突导致系统死机。排查过程：
1. 怀疑是串口 1 和串口 2 冲突
2. 查清：串口 1 是电机控制器 DMA 实时转发接口
3. 把 USART3 从 PB10 换到 PA7
4. 最终发现是 **CubeMX 自动把 USART1 的 DMA 设置删掉了**
5. 修复后，ACK 反馈队列创建成功
> **核心教训**：CubeMX 重新生成代码时会无声地删掉你的配置。每次重新生成后必须逐一核对关键外设设置。

**12-21 ~ 12-22**
**CAN 通信首次双机跑通！**
两块 STM32F103，Model-A 发 → Model-B 收 → LED 跳变。逻辑分析仪留存时序图。
踩坑：旧版 Model-B 的板子连回环都实现不了，换 F103 解决。**"原来同一型号的不同板子个体差异可以这么大"**。

**12-24**
尝试将 CAN 融入现有控制代码。**失败，代码炸了**。"了解到 github 有恢复到任意 commit 版本的功能"——Git 分支的概念第一次真正用上。
"用 ai 抽离 can 代码（不能使用），差点回不去"——**AI 给的 CAN 代码合并后直接搞崩，靠 Git 回滚救命**。
这一天经历：🚧 写CAN代码 → 💥 炸了 → 🔄 git revert → 📚 学分支 → 🌿 创建第一个分支并推送。

**12-25**
**UartToCan 网关项目创建！**
独立项目，专门做"串口命令 → CAN 网络"的桥接。
测试三端：发送端(串口) → 中介端(UartToCan) → 接收端(CAN Slave)。
**成功实现外部串口 → 本地 CAN 网络 → CAN 控制电机**。
踩坑发现：CAN 模块间共地会产生噪声 → 改为星型单点接地 → 噪声消失。

**12-26**
继续改进 UartToCan。在 CubeMX（CMake 下）自定义枚举类型 `CanCmd_t`。解决 FreeRTOS 堆栈溢出问题（堆栈设过大反而报错）。

**12-27**
（仅 1 行）"争取留校"——假期去向。

**12-28**
**成功实现双电机控制！** 单命令控双电机 + 双命令单控都已实现。直连 CAN 模块即可。"不涉及对 can 模块电阻进行操作"。

**02-18**
**🎯 底盘架构确定日——非常重要的一天。**
和 AI 做了一次非常深入的系统架构讨论，内容涉及：
1. **单路 CAN vs 双路 CAN**：结论——单路 1Mbps CAN 在 4~8 电机规模下完全足够
2. **SYNC 同步机制**：主控先下发目标 → 电机缓存 → 发送 SYNC → 所有电机同步执行。同步误差 ~几十微秒
3. **三层安全机制**：电机节点级（5ms 超时停机/电流保护/看门狗）→ 主控级（心跳/故障隔离/急停）→ 系统级（物理急停/电源断电）
4. **FreeRTOS 角色**：F103 电机节点慎用 RTOS（避免高频任务被干扰），F446 主控适合 RTOS
5. **micro-ROS 可行性**：F446 上可行但有内存压力，不必过早部署
6. **Linux + STM32 vs 纯 MCU**：当前 4~8 电机规模，纯 MCU 架构是最优解
7. **结论**："所有 100Hz 以上闭环必须在 MCU 内完成。Linux 绝不能参与高速闭环。"
> **这份讨论标志着从"学技术"到"做架构决策"的质变。** 不是问"哪个好"，而是分析 trade-off 后做决定。

### 10.4 AI 使用模式分析

从笔记中可以清楚看到 AI 的使用经历了三个阶段：

**阶段 1（2025-09→12）"救命模式"**
- 提问："为什么我的串口收不到数据"
- 使用：Copilot 偶尔帮写代码片段
- 记录：极少记录 AI 对话，用 ChatGPT 但没留存链接

**阶段 2（2026-01→03）"导师模式"**
- 提问："帮我分析这个代码架构有什么问题" / "这个 bug 可能是什么原因"
- 使用：ChatGPT 分析代码、Gemini 查资料、Claude 写代码片段

**阶段 3（2026-04→07）"协作者模式"**
- 提问：把完整的代码丢给 AI，"帮我审查这段代码的架构和潜在问题"
- 使用：Claude 做架构设计、代码审查、文档撰写；DeepSeek API 接入
- 记录：几乎所有关键决策都有 AI 对话链接存档。每篇笔记顶部通常有 ChatGPT/Gemini 链接

**关键观察**：AI 的参与度不是"变多了"，而是**变深了**——从"给答案"到"帮思考"。

### 10.6 综合优点

1. **架构嗅觉好** — CAN 分布式、UART↔CAN 网关、PC+MCU 混合架构，对于新手团队来说是极其正确的选择
2. **保护意识强** — 堵转保护、遥控超时 1s 急停、软件限位、锁定/解锁——一个新手团队做全了这些
3. **文档习惯优秀** — 项目文档 30+ 篇 + 个人笔记 235 篇。从"贴图"进化到"文字+代码+图片"
4. **AI 使用正确** — 从"给我代码"到"帮我理解为什么"，用 AI 做导师而非替代品
5. **遇到问题不绕路** — 每个坑都踩了、记录了、理解了
6. **工具链主流** — CMake + Ninja + GCC + JLink + Ozone + Git，没有用 Keil/IAR 把自己锁死

### 10.7 综合不足

1. **时间规划过于激进** — 从零起步到比赛只有 10 个月，前 4 个月都在补基础，真正系统集成只有最后 3~4 个月
2. **硬件损坏代价** — UNIT4 烧毁是代价最高的单一故障，根因不是技术不行，而是缺少系统级验证流程
3. **测试覆盖不完整** — R1 机械臂未测试、关节速度迁移后遗留问题、传感器融合未校准
4. **记录断裂（2026-01）** — 丢了 30 天的决策上下文
5. **缺少端到端闭环验证** — 每一块都会一点，但"ROS→MCU→电机→反馈→ROS"的完整链路没有正式验证通过

### 10.8 关键教训

1. **方向取反做自动化验证** — 所有电机方向用脚本逐一确认，不靠人肉记"三处取反"
2. **先打通端到端再优化** — 每个 Phase 的第一步是"最简链路跑通"
3. **测试清单写下来** — 测试靠记忆 = 测不全。参考 `测试指南.md`
4. **关键硬件备余量** — 电机、驱动板至少备 1 份
5. **记录中断是最大浪费** — 每天至少 3 行，即使生病也写一行 `[请假]`

**劣势：**

2. **容易设备驱动学习** — 新硬件/新模块/新平台容易被吸引，"不要成为设备收藏者"
3. **数学基础** — 线代/概率/优化需要补
4. **C++ 偏弱** — 机器人核心（Eigen/PCL/OpenCV/ROS2 C++）需加强
