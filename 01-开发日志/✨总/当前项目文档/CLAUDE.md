## 疑难问题排查：先搜索，后推理

! 遇到难以解决的问题（事实不确定、报错原因不明、陌生工具/API、信息可能过时等），
  先做网页搜索（WebSearch/WebFetch），用搜索结果核实后再自行推理；不得凭猜测直接下结论
- 搜索范围优先级：Google（搜索引擎）→ 官方文档/技术社区/论坛
  （如 Stack Overflow、GitHub Issues、CSDN）→ 个人网站/博客
- 搜索结果不足以定论时，基于结果推理并标注不确定点，不得编造来源或细节

## 工具选型：官方路径优先

! 默认使用官方工具/API/文档（官方优先），官方路径走不通时，先停下来询问用户，
  再考虑第三方方案
- 例：ROS2 bag 分析默认用官方 `rosbag2_py`（ROS2 自带、零安装），不先用第三方 `rosbags` 库
- 教训（2026-08-06）：bag 分析先用了第三方 rosbags 库，因版本 API 差异反复踩坑，
  换回官方 rosbag2_py 一次通过

## 操作执行方式：先问再做，给用户动手空间

! 执行有实际影响的操作前（命令行、git 操作、文件修改、硬件调试等），先询问用户：
  由 AI 直接执行，还是由 AI 给出「操作指令 + 预期现象/验证方法」让用户亲手操作
- 原因：全程代劳会剥夺用户动手排障的收获；学习性操作优先考虑交给用户动手
- 纯查询/读取（读文件、查状态、搜索信息）不受此限，不必询问
- 同一任务的连续小操作归并成一次询问，不逐条打断

## 任务切换：先汇报，征求同意后再动手

! 现行任务未完成、或用户最新指令未覆盖的新动作，不得擅自切换任务方向
  （整理文档 → 排障、实现 → 验证、排查 → 提交等）
- 一个任务完成后：先汇报结果 + 给出下一步选项，由用户决定走哪条，再动手
- 判断标准：新动作是否在用户当前指令的范围内；超出即先问
- 教训（2026-08-25）：用户指令「整理文档」完成后，未经同意直接开始排障（读日志/查进程），
  被用户叫停——任务切换和操作执行一样，必须先问再做

## 原始数据留存：用户粘贴的数据必须落盘

! 用户发来的原始数据（命令输出、日志、录制记录、数据表、对话原文等），必须存到本地文件，
  并附加「session 话题 + 日期时间」标注（文件名或文件头）
- 落盘位置：**项目内 doc/raw_data/**（如 `r2_integration/doc/raw_data/`），文件名示例：
  `raw_<话题>_2026-08-25_1315.txt`，文件头注明来源与 session 话题
- 一般性地址（通用写法，不写死项目/日期）：`<项目根>/doc/raw_data/raw_<话题>_<YYYY-MM-DD>_<HHMM>.txt`
- 原始数据不入 git 提交（提交前 git status 确认；必要时 .gitignore 排除）
- 目的：原始数据只在对话里会随上下文压缩/会话结束而丢失；落盘后可回溯、可复查
- 教训（2026-08-25）：用户粘贴 N97 rosbag 录制日志后，未落盘直接消费——证据只存在于
  对话上下文，压缩/结束即丢失；先落盘再分析

## 编辑纪律：只增不删，删除前先确认

! 修改全局规则/文档规范（CLAUDE.md、standards.md 等）时，一般情况只增不删：
- 新增内容直接写；删除/改写既有内容前，先向用户确认
- 需要通用写法时保留原文，另加一般性写法（增补优于替换）
- 教训（2026-08-25）：通用化改写「原始数据留存」落盘位置时直接删掉原示例，
  被用户叫停「不要删」

## 操作完成后的自查

! 完成操作（写文档/改代码/提交/部署等）后，必须自查一遍结果是否正确：
- 对比相关文档核验（有文档的话）；文档需注意**日期是否够新、是否仍可用**
- 文档状态不确定（过时/缺失/矛盾/拿不准）时，**询问用户确认**，不得自行推断
- 教训（2026-08-06）：写 project_status.md 时未先读 g354-wiring.md/chassis_definition.md
  等既有文档，凭记忆写错 G354/CAN/雷达接线，被用户纠正；先读文档再动手，写完再对照自查

## 进程卫生纪律（2026-08-25 定）

! AI 启动的长驻进程必须由 AI 负责关闭；禁止自行调用可能存在「关闭不自杀 / 残留缓存」的操作
- AI 调用任何会启动长驻进程的命令（ros2 launch/run、后台节点、服务器、docker、rosbag play、
  守护服务等），**完成后必须主动关闭自己启动的进程**；确实需要保留的，必须明确告知用户
  "该进程仍在运行 + 关闭命令"
- 涉及缓存/常驻服务的操作（ros2 daemon、DDS 发现缓存、colcon 缓存等），用后按需清理
  （如 `ros2 daemon stop`）或说明当前状态
- **周期性自查提醒**：每几个话题（或每个排障/调试阶段收尾时），提醒用户自查系统残留进程：
  `ps aux | grep -iE "ros|nav2|rviz|velodyne|docker|server" | grep -v grep`
- 教训（2026-08-25）：AI 调试遗留 nav2_costmap_2d + static_transform_publisher 进程
  在 VM 上未关闭数小时，通过同网段 FastDDS 多播发现污染 N97 的 `ros2 node list`（"杀不掉"），
  用户排查良久；"杀不掉的节点 = 节点不在本机"（详见 ros2-ops.md §10）

## 项目推进原则：先端到端，再优化

! 项目推进遵循「先本地最小闭环跑通，后续再谈优化」：
- **端到端优先**：基础层够用即止，优先打通完整链路（例：R2 里程计 0.27m 闭环已够用，
  应立即启动建图/导航/避障，不再打磨精度）；完整贯通后，再回头收尾优化
- **最小项目先行**：先做能跑通的最小项目，遇到实际问题再反向补理论（工程驱动理论，
  而非理论驱动工程）；不要脱离任务学技术
- **一超多强**：一条主线深做，其他模块只要求能沟通接口、看懂约束
- **可验证成果**：每个阶段交付须有量化验收标准（数据/指标），不用"效果良好"这类空话；
  项目完成后留运行视频、日志、参数记录、问题复盘、代码仓库（作品集资产）
- **排障纪律**：每次只加一个变量；记录期望/实际数据，出问题回溯数据而非盯现象
- **安全前置**：首次实机测试用降额参数（速度 20%/力矩 30%），上电前检查清单，
  失控先拍急停，不赌运气
- 反模式：追热点频繁换方向（"设备收藏者"）、跳过端到端直接优化局部、
  仿真通过就以为真机没问题（Sim2Real gap 是必考题）
- 方法来源：Lain《机器人工程师学习计划》（对照见 `Lin_note/.../gpt阶段性总结/Lain_机器人学习计划_对照.md`）

## 多机环境与验证纪律

! 涉及多机操作时，先确认「当前操作对象是哪台机器」，再动手
- AI 工具（Bash/Edit/文件访问）运行在 **VM**（lin-virtual-machine）；实车/部署目标机是 **N97**（lin-Default-string, 192.168.1.210）
- 源码工作区 VM 与 N97 各一份独立副本：改代码在 VM，同步走 git push → N97 pull（见 standards.md 1.10）；
  用户贴出的运行/实车反馈来自 N97——**不要用 VM 的 install/build 状态去解释 N97 的行为**
- 改代码后验证前，先确认目标进程加载的是**新构建**：colcon build + 重启进程，否则测到的是旧代码
- ROS2 构建产物检查：console_scripts 入口（`install/.../lib/<pkg>/<script>`）是 import 壳不含源码；
  验证构建是否更新应 grep `install/<pkg>/lib/python3*/site-packages/<pkg>/` 里的源码
- 教训（2026-08-11）：r2_bringup 审查修复中，在 VM 上诊断 N97 的 install 时间戳/构建产物，
  全部对不上——两个工作区相互独立，白排查一圈；先问清机器再操作
