### 程序测试技巧

> [!NOTE]
> ## ✅ 解决方法（调试阶段推荐）
> 
> ### 方法 1（最干净）：显式“使用”它
> 
> int c = a + b;  
> (void)c;    // 告诉编译器：我就是要用它
> 
> 这是嵌入式工程最常见的写法。
> 
> ---
> 
> ### 方法 2：打 log
> 
> printf("%d\n", c);
> 
> 但你现在是裸机 + RTOS，不一定开了重定向。
> 
> ---
> 
> ### 方法 3：设为 volatile（调试技巧）
> 
> volatile int c = a + b;
> 
> 这样编译器不会优化掉它。

### 何时能够调试？（空心红圈、灰）

1. 出现实心红圆、空心红圈的这一列上，在没有代码、存在注释的行都无法点击

> [!NOTE]
> 这个现象**完全正常**，而且你已经踩到**调试器工作原理的核心边界**了。  
> 我分层把“为什么不能点”“什么情况下能点”“怎么判断是不是你环境有问题”一次说清。
> 
> ---
> 
> ## 一、结论先行（你记住这三条就够）
> 
> **1️⃣ 只能在「可执行代码行」打断点**  
> **2️⃣ 注释行 / 空行 / 只有 `}` 的行，永远不能打断点**  
> **3️⃣ 断点不是 VSCode 的功能，而是由“编译结果里的指令地址”决定的**
> 
> 你现在看到的行为，说明：  
> 👉 **编译、符号、调试器全部是正常的**
> 
> ---
> 
> ## 二、为什么「注释行」不能点？（根本原因）
> 
> 调试器的断点，本质是：
> 
> > **在某一条“CPU 指令地址”上停下来**
> 
> 而：
> 
> ```c
> // 这是注释
> /* 这是注释 */
> ```
> 
> 在编译阶段会发生什么？
> 
> 👉 **直接被编译器删掉**  
> 👉 **不会生成任何机器指令**  
> 👉 **ELF 里根本不存在对应地址**
> 
> 所以：
> 
> - VSCode 左侧那一列只是「UI」
>     
> - 真正决定能不能下断点的是：  
>     **这一行是否能映射到 ELF 里的指令**
>     
> 
> **没有指令 = 没有断点**
> 
> ---
> 
> ## 三、哪些行「一定不能」打断点？
> 
> 下面这些你以后一眼就要识别出来 👇
> 
> ### ❌ 不能打断点的行
> 
> ```c
> // 注释
> /* 注释 */
> 
> /* 
>    多行注释
> */
> 
> ```
> 
> ```c
> }          // 只有大括号
> ```
> 
> ```c
> #define X 10   // 纯宏定义（通常不行）
> ```
> 
> ```c
> int a;      // 只声明、无执行（有时能，有时不）
> ```
> 
> ```c
> typedef int myint;   // 类型定义
> ```
> 
> ---
> 
> ## 四、哪些行「一定可以」打断点？
> 
> ### ✅ 可执行语句 = 可断点
> 
> ```c
> int a = 5;
> ```
> 
> ```c
> c = a + b;
> ```
> 
> ```c
> if (a > b)
> ```
> 
> ```c
> while (1)
> ```
> 
> ```c
> xQueueSend(...);
> ```
> 
> ```c
> vTaskDelay(100);
> ```
> 
> ```c
> HAL_GPIO_WritePin(...);
> ```
> 
> 这些都会生成 **真实的 CPU 指令**。
> 
> ---
> 
> ## 五、你看到的「实心红点 / 空心红圈」分别代表什么？
> 
> 这是重点。
> 
> ### 🔴 实心红点（已绑定）
> 
> > ✔ 断点已经成功绑定到**真实指令地址**
> 
> 说明：
> 
> - 该行有可执行代码
>     
> - 编译器没有优化掉
>     
> - ELF 里有符号 + 地址
>     
> - 调试器确认 OK
>     
> 
> 这是**最理想状态**
> 
> ---
> 
> ### 🔴 空心红圈（逻辑断点 / 未解析）
> 
> > ⚠ VSCode 接受了你的断点请求  
> > ⚠ 但调试器还没找到对应指令
> 
> 常见原因：
> 
> 1️⃣ 程序还没启动 / 没加载 ELF  
> 2️⃣ 该行代码被优化掉  
> 3️⃣ 你点在了「看似有代码，实际没指令」的地方  
> 4️⃣ 这是宏展开、内联函数、头文件
> 
> 一旦程序真正运行、符号加载成功：
> 
> 👉 要么变成实心  
> 👉 要么直接消失
> 
> ---
> 
> ## 六、你现在这个现象说明了什么？（这是好消息）
> 
> 你说的是：
> 
> > 「在没有代码、存在注释的行都无法点击」
> 
> 这说明：
> 
> ✅ VSCode 正确识别“不可执行行”  
> ✅ 调试插件和 ELF 映射是对的  
> ✅ 不是假断点  
> ✅ 不是源码-ELF 不匹配  
> ✅ 不是 Ozone / GDB 出问题
> 
> **反而是“新手最容易误以为有问题、但实际上非常健康”的状态**
> 
> ---
> 
> ## 七、一个关键对比实验（建议你立刻做）
> 
> 你在 `main()` 里试这三行：
> 
> ```c
> // A. 注释行
> // test comment
> 
> // B. 可执行行
> int test = 123;
> 
> // C. 空语句
> ;
> ```
> 
> 你会看到：
> 
> |行|能否点断点|
> |---|---|
> |注释|❌|
> |`int test = 123;`|✅|
> |`;`|❌|
> 
> 这能让你**彻底建立直觉**。
> 
> ---
> 
> ## 八、真正的进阶：RTOS 场景下你要注意的
> 
> 在 FreeRTOS 里，**更容易遇到“点不了”的情况**：
> 
> ```c
> for (;;)
> {
>     // 空循环体
> }
> ```
> 
> 你不能点在 `{` 或 `}` 上  
> 你必须点在：
> 
> ```c
> for (;;)
> {
>     vTaskDelay(100);
> }
> ```
> 
> 👉 **只有产生指令的地方，才有调试意义**
> 
> ---
>

>

>

>     
> - 区分「代码问题 vs 编译器问题」
>     
> - 理解断点 ≠ 文本行
>     
> 
> 这一步，**99% 的 MCU 初学者从没搞清楚过**。
