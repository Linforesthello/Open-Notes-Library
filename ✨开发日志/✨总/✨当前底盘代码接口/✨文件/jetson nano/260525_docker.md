## 2. 初始问题：Docker Hub 被墙

### 2.1 现象描述

用户执行 `jetson-inference/docker/run.sh` 脚本，该脚本自动执行 `docker pull dustynv/jetson-inference:r32.7.1`，但拉取失败：

```
Error response from daemon: Get "https://registry-1.docker.io/v2/":
net/http: request canceled while waiting for connection
(Client.Timeout exceeded while awaiting headers)
```

### 2.2 根因分析

#### 网络拓扑

Jetson Nano 位于中国大陆网络环境下。GFW（Great Firewall）对 Docker Hub 的域名 `registry-1.docker.io` 以及 `auth.docker.io` 进行了 DNS 污染和 IP 封锁，导致：

1. **TCP 三次握手无法完成** — Docker 守护进程无法与 Docker Hub 建立连接
2. **连接等待超时** — 默认超时时间后返回 `Client.Timeout`
3. **镜像拉取流程断裂** — Docker 的 pull 流程在获取镜像清单（manifest）阶段即失败

#### 重试验证

用户手动执行两次 `docker pull dustynv/jetson-inference:r32.7.1` 均以同样的超时错误失败，确认不是偶发网络抖动。

### 2.3 初始假设

**假设 1**：配置 Docker Registry Mirror 可以解决问题

- *依据*：国内各云服务商提供 Docker Hub 镜像加速器
- *预期*：Docker 通过镜像源拉取，绕过直接连接 Docker Hub

**假设 2**：配置 HTTP 代理可以解决问题

- *依据*：如果有代理工具，Docker 通过代理访问外网
- *状态*：用户明确表示无代理可用，此路不通

**假设 3**：本地 Docker Build 可以规避

- *依据*：jetson-inference 仓库中有 Dockerfile
- *预期*：本地构建不依赖 Docker Hub 拉取

## 3. 第一轮尝试：配置 Registry Mirror

### 3.1 方案设计

选择三个国内常用的 Docker Hub 镜像加速器：

| 镜像源 | URL | 特点 |
|--------|-----|------|
| **中科大 (USTC)** | `https://docker.mirrors.ustc.edu.cn` | 教育网，传统稳定 |
| **腾讯云** | `https://mirror.ccs.tencentyun.com` | 企业级 CDN |
| **阿里云** | `https://registry.cn-hangzhou.aliyuncs.com` | 国内最大容器镜像服务 |

### 3.2 配置操作

写入 `/etc/docker/daemon.json`：

```json
{
  "registry-mirrors": [
    "https://docker.mirrors.ustc.edu.cn",
    "https://mirror.ccs.tencentyun.com",
    "https://registry.cn-hangzhou.aliyuncs.com"
  ],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

执行命令：

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json << 'EOF'
{...上面的 JSON 内容...}
EOF
sudo systemctl restart docker
```

### 3.3 验证配置生效

```bash
sudo docker info
```

输出确认配置生效：

```
Registry Mirrors:
  https://docker.mirrors.ustc.edu.cn/
  https://mirror.ccs.tencentyun.com/
  https://registry.cn-hangzhou.aliyuncs.com/
```

### 3.4 拉取测试

```bash
docker pull dustynv/jetson-inference:r32.7.1
```

**结果：❌ 仍然失败**

错误信息与之前完全相同，依然超时在 `registry-1.docker.io`。

### 3.5 初步分析

- 配置本身没有问题（`docker info` 确认读取成功）
- 但 mirror 机制仅在**层（layer）下载阶段**生效
- 初始的**镜像清单（manifest）获取**和**认证（auth）** 仍需要访问 `registry-1.docker.io`
- 如果 Docker Hub 完全不可达，mirror 的加速能力无法发挥作用
- 或者：配置的三个 mirror 中有不可达的，Docker 在 mirror 上失败后 fallback 到原始 registry

## 6. 第三轮尝试：测试镜像源连通性

### 6.1 诊断方法

使用 curl 测试各镜像源的 HTTP 可达性：

```bash
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://registry.cn-hangzhou.aliyuncs.com/v2/
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://mirror.ccs.tencentyun.com/v2/
```

### 6.2 测试结果

| 镜像源 | HTTP 状态码 | 响应时间 | 结论 |
|--------|------------|----------|------|
| 阿里云 `registry.cn-hangzhou.aliyuncs.com` | `401` | 0.37s | ✅ **可达** |
| 腾讯云 `mirror.ccs.tencentyun.com` | `000` | 0.028s | ❌ **不可达** |

### 6.3 结果分析

- **阿里云返回 401**：这是正常的 HTTP 认证响应，说明服务器存活并可正常响应请求。401 意味着"需要认证"，但说明 TCP 连接和 TLS 握手均成功完成
- **腾讯云返回 000**：curl 在收到任何 HTTP 状态码前已失败。0.028s 的超快失败时间表明很可能是 DNS 解析失败或 SNI 阻断，而非正常连接超时
- **推测中科大 (USTC) 同样不可达**：同属教育网/科研机构，近期也有访问限制的公开报告

### 6.4 假设修正

多个 mirror 配置导致的问题链：

```
用户配置了 3 个 mirror（USTC、腾讯云、阿里云）
         ↓
Docker 按顺序尝试 mirror
         ↓
USTC → ❌ 不可达（快速失败）
         ↓
腾讯云 → ❌ 不可达（快速失败）
         ↓
阿里云 → ⚠️ 可达但返回 401
         ↓
Docker 对 401 的处理 → 回退到原始 registry（Docker Hub）
         ↓
Docker Hub → ❌ 被墙 → 超时失败
```

**关键修正**：不应该配置多个 mirror，应该只保留可达的阿里云。

### 7.1 精简配置

```bash
sudo tee /etc/docker/daemon.json << 'EOF'
{

    "max-file": "3"
  }
}
EOF
sudo systemctl restart docker
```

### 7.2 测试

```bash
docker pull dustynv/jetson-inference:r32.7.1
```

**结果：❌ 依然失败**

同样的错误，仍然提示 `registry-1.docker.io` 连接超时。

### 7.3 Direct Pull 测试

```bash
docker pull registry.cn-hangzhou.aliyuncs.com/dustynv/jetson-inference:r32.7.1
```

**结果：❌ 被拒绝**

```
Error response from daemon: pull access denied for
registry.cn-hangzhou.aliyuncs.com/dustynv/jetson-inference,
repository does not exist or may require 'docker login':
denied: requested access to the resource is denied
```

### 7.4 根因深入分析

#### 阿里云 `registry.cn-hangzhou.aliyuncs.com` 是什么？

- 这是阿里云**自己的容器镜像仓库**，不是 Docker Hub 的透明代理
- 它只服务于阿里云用户上传的镜像，不缓存/代理 Docker Hub 的公共镜像
- 两种模式的区别：

| 模式 | 工作原理 | 对本场景 |
|------|---------|---------|
| **Registry Mirror** | Docker 将 Docker Hub 请求透明转发到 mirror URL | 需要 mirror 端实现完整的 v2 API 代理 |
| **独立 Registry** | 需要用户手动 `docker pull registry/namespace/image` | 镜像必须存在于该 registry 上 |

#### Docker Mirror 的真正工作机制

1. 用户执行 `docker pull dustynv/jetson-inference:r32.7.1`
2. Docker 守护进程解析镜像名为 `registry-1.docker.io/dustynv/jetson-inference:r32.7.1`
3. Docker 尝试从 mirror URL 获取镜像的 **manifest**
4. 如果 mirror 支持代理 Docker Hub，它返回 manifest，Docker 从 mirror 拉取 layers
5. 如果 mirror 不支持（如阿里云），基于不同 Docker 版本，Docker 会回退到 `registry-1.docker.io`
6. `registry-1.docker.io` 被墙，连接超时

#### Docker Mirror 与 Proxy 的本质区别

```
Registry Mirror 模式:
  docker pull image:tag
       ↓
  Docker Daemon ──→ Registry Mirror ──→ Docker Hub
                     (仅数据层代理，认证仍走 Docker Hub)

Docker Daemon Proxy 模式:
  docker pull image:tag
       ↓
  Docker Daemon ──→ HTTP Proxy ──→ Docker Hub
                     (全流量代理，包括认证)
```

### 7.5 阿里云 Mirror 不可行的真实原因

1. `registry.cn-hangzhou.aliyuncs.com` 作为 Docker Hub mirror 的实现有缺陷
2. Docker 在 mirror 返回 401 后会尝试回退到原始 registry
3. 阿里云真正的 Docker Hub 加速地址是 `https://<your-code>.mirror.aliyuncs.com`（需要阿里云账号开通），不是通用的公共地址

## 8. 第五轮尝试：本地 Docker Build

### 8.1 方案概述

由于 jetson-inference 仓库包含 Dockerfile，可以直接在本地构建镜像，无需从 Docker Hub 拉取。

```bash
cd ~/jetson-inference
docker build -t dustynv/jetson-inference:r32.7.1 -f Dockerfile .
```

### 8.2 构建过程解析

Dockerfile 共 26 个步骤（Step 1/26 ~ Step 26/26）。

#### 成功部分 ✅

**Step 1/26**：基础镜像拉取

```dockerfile
ARG BASE_IMAGE=nvcr.io/nvidia/l4t-pytorch:r32.4.3-pth1.6-py3
FROM ${BASE_IMAGE}
```

- 镜像源：`nvcr.io`（NVIDIA GPU Cloud Registry）
- 结果：✅ **完全成功**，所有 30 层全部拉取完成
- 关键发现：**NVIDIA 的 registry 在中国大陆可达！**

**Steps 2-5**：环境变量和工作目录设置

```dockerfile
ENV DEBIAN_FRONTEND=noninteractive
ENV SHELL /bin/bash
WORKDIR /jetson-inference
```

- 这些步骤全部成功

#### 失败部分 ❌

**Step 6/26**：依赖包安装

```dockerfile
RUN add-apt-repository --remove "deb https://apt.kitware.com/ubuntu/ $(lsb_release --codename --short) main" && \
    apt-get update && \
    apt-get purge -y '*opencv*' || echo "existing OpenCV installation not found" && \
    apt-get install -y --no-install-recommends \
        cmake nano mesa-utils lsb-release \
        gstreamer1.0-tools gstreamer1.0-libav gstreamer1.0-rtsp \
        gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-plugins-ugly \
        libgstreamer-plugins-base1.0-dev libgstreamer-plugins-good1.0-dev \
        libgstreamer-plugins-bad1.0-dev ...
```

#### 执行路径追踪

这个 RUN 命令是一个复杂的 shell 链式操作，需要仔细分析其执行路径：

```
Step 6 的 RUN 命令结构（简化）：

add-apt-repository --remove "..."  →  ❌ 失败（命令不存在，exit 127）
        &&
apt-get update                    →  被跳过（前序失败）
        &&
apt-get purge -y '*opencv*'       →  被跳过（前序失败）
        ||                         ← OR 短路：前面 && 组失败，到这里
echo "existing OpenCV ..."        →  ✅ 执行（exit 0，命令成功）
        &&
apt-get install -y ...            →  ❌ 执行但失败（没有 apt update）
```

**关键问题**：`add-apt-repository` 命令在基础镜像中不存在（不是在 Ubuntu 核心包中，需要额外安装 `software-properties-common`），导致 `apt-get update` 也被跳过，包列表为空，所有安装包找不到。

#### 构建失败输出

```
E: Package 'cmake' has no installation candidate
E: Unable to locate package nano
E: Unable to locate package mesa-utils
E: Unable to locate package lsb-release
E: Unable to locate package gstreamer1.0-rtsp
E: Unable to locate package libgstreamer-plugins-base1.0-dev
...
The command returned a non-zero code: 100
```

### 8.3 重要发现

虽然构建失败，但有一个关键收获：

> **NVIDIA NGC Registry（nvcr.io）在中国大陆是可达的！**

这为后续提供了重要的基础镜像通路。

## 9. 第六轮尝试：docker.1ms.run — 最终解决方案

### 9.1 方案原理

`docker.1ms.run` 是一个社区维护的 Docker Hub 反向代理，其核心优势：

| 特性 | 传统 Registry Mirror | docker.1ms.run |
|------|--------------------|----------------|
| 认证代理 | ❌ 不代理 | ✅ 完整代理 |
| Manifest 代理 | ❌ 不代理 | ✅ 完整代理 |
| Layer 代理 | ✅ 代理 | ✅ 代理 |
| 需要 Docker Hub 可达 | ❌ 需要 | ✅ 不需要 |
| 在中国可用性 | ⚠️ 不稳定 | ✅ 专门为 CN 用户设计 |

### 9.2 配置操作

```bash
sudo tee /etc/docker/daemon.json << 'EOF'
{
  "registry-mirrors": ["https://docker.1ms.run"]
}
EOF
sudo systemctl restart docker
```

### 9.3 拉取测试

```bash
docker pull dustynv/jetson-inference:r32.7.1
```

### 9.4 拉取过程解读

```
r32.7.1: Pulling from dustynv/jetson-inference
f46992f278c2: Already exists      ← 之前 build 已拉取的层（共用）
d0ec296fcb76: Already exists      ← 来自 nvcr.io 的层依然可用
... (30+ 层显示 Already exists)
75b7f111acd3: Pull complete       ← 新增层从 1ms.run 拉取
aed6bb8d6796: Pull complete
... (15+ 新层依次拉取完成)
Digest: sha256:7ee3ab60052aa2372e4d17ba428eeac4f34fb16ffec5dec6b5cb984495d42d58
Status: Downloaded newer image for dustynv/jetson-inference:r32.7.1
docker.io/dustynv/jetson-inference:r32.7.1
```

**结果：✅ 大成功！**

完整的 `dustynv/jetson-inference:r32.7.1` 镜像成功下载到 Jetson Nano。

### 9.5 关键成功因素

1. **全代理模式**：代理包括认证在内的全部 Docker Hub 流量
2. **镜像层缓存复用**：之前 `docker build` 已经从 `nvcr.io` 拉取了基础镜像层，这些层 SHA 相同，直接复用
3. **国内优化线路**：专为中国大陆网络环境设计

## 10. 第七步：配置 NVIDIA Container Runtime

### 10.1 新问题

镜像拉取成功后，执行 `docker/run.sh` 启动容器：

```bash
cd ~/jetson-inference
docker/run.sh
```

**失败：**

```
docker: Error response from daemon: Unknown runtime specified nvidia.
```

### 10.2 根因分析

`docker/run.sh` 脚本中指定了 `--runtime nvidia` 参数，但 Docker 守护进程不知道 nvidia runtime。

Jetson Nano 上 Docker 的 GPU 访问架构：

```
Docker Container
      ↑
nvidia-container-runtime ← 需要安装
      ↑
nvidia-container-toolkit  ← 需要安装
      ↑
libnvidia-container       ← 需要安装
      ↑
NVIDIA 驱动 (L4T)         ← 系统已预装
      ↑
Jetson Nano GPU (Maxwell 架构, 128 CUDA cores)
```

### 10.3 解决方案

```bash
# 安装 nvidia-container-runtime
sudo apt-get update
sudo apt-get install -y nvidia-container-runtime

# 配置 Docker 守护进程
sudo tee /etc/docker/daemon.json << 'EOF'
{
  "registry-mirrors": ["https://docker.1ms.run"],
  "runtimes": {
    "nvidia": {
      "path": "/usr/bin/nvidia-container-runtime",
      "runtimeArgs": []
    }
  }
}
EOF

# 重启 Docker
sudo systemctl restart docker
```

**备选方案**（如果 `nvidia-container-runtime` 包找不到）：

```bash
sudo apt-get install -y nvidia-docker2
sudo systemctl restart docker
```

### 10.4 启动验证

```bash
cd ~/jetson-inference
docker/run.sh
```

**结果：✅ 成功进入容器**

```
root@lin-desktop:/jetson-inference#
```

提示符变成 `root@...` 表明已进入容器内部，拥有完整的 GPU 访问权限。

## 12. 安全退出与下次恢复

### 12.1 安全退出容器

在容器内执行：

```bash
exit
```

或按快捷键：**Ctrl + D**

**关于 `--rm` 模式**：

`docker/run.sh` 默认使用 `docker run --rm` 参数，这意味着：
- 退出容器后，**容器会被自动删除**
- 容器内未保存的修改（额外安装的包、修改的配置文件）会丢失
- 但挂载卷中的数据（`/jetson-inference/data/` 等）会保留

### 12.2 关机后恢复流程

**Step 1**：开机启动 Jetson Nano（等待系统完全启动）

**Step 2**：打开终端

**Step 3**：执行以下命令

```bash
cd ~/jetson-inference
docker/run.sh
```

**Step 4**：等待容器启动，即可继续使用

### 12.3 数据持久化策略

| 数据类型 | 存放位置 | 是否持久化 |
|---------|---------|-----------|
| 容器内安装的包 | 容器内任意位置 | ❌ 退出后丢失 |
| 模型权重 / 脚本 | `~/jetson-inference/data/` 等挂载卷 | ✅ 永久保存 |
| 自定义配置 | `~/jetson-inference/` 下（非容器内） | ✅ 永久保存 |

**如果需要持久化容器内的修改**：

方案 A：将文件保存在挂载的宿主机目录中
```bash
# 在容器内将数据复制到挂载卷
cp /容器内/文件 /jetson-inference/data/
```

方案 B：基于当前容器创建新镜像
```bash
# 在宿主机上（容器外）
docker commit <容器名或ID> my-custom-jetson-inference:latest
docker run --runtime nvidia ... my-custom-jetson-inference:latest
```

## 15. 附：故障诊断思维导图

### 15.1 问题树

```
Jetson Nano Docker Hub 不可用
│
├─ 方案 A：Registry Mirror（镜像加速器）
│  ├─ USTC docker.mirrors.ustc.edu.cn
│  │  └─ ❌ DNS/GFW 不可达
│  ├─ 腾讯云 mirror.ccs.tencentyun.com
│  │  └─ ❌ DNS/GFW 不可达
│  ├─ 阿里云 registry.cn-hangzhou.aliyuncs.com
│  │  ├─ ❌ 不是 Docker Hub 透明代理
│  │  └─ Docker 回退到直连 Docker Hub → ❌
│  └─ docker.1ms.run（社区代理）
│     └─ ✅ 完整代理认证+数据 → 成功！
│
├─ 方案 B：HTTP 代理
│  └─ 用户无可用代理 → ❌ 不适用
│
├─ 方案 C：本地 Docker Build
│  ├─ ✅ nvcr.io 基础镜像可达
│  ├─ ❌ Dockerfile apt-get 链式失败
│  └─ add-apt-repository 命令不存在
│
├─ 方案 D：离线传输
│  └─ 用户未尝试（需要额外机器）
│
└─ 最终结果
   ├─ ✅ 镜像成功拉取
   ├─ ✅ NVIDIA Runtime 配置
   ├─ ✅ 容器成功启动
   └─ ✅ 实时物体检测 ~23FPS
```

### 15.2 核心教训

1. **国内网络环境下 Docker Hub 不可用**是已知事实，解决的关键是找到可用的替代通路
2. **传统 Registry Mirror（阿里云/中科大/腾讯云）** 在 Docker Hub 完全被墙时无效，它们只代理层数据
3. **社区全代理（docker.1ms.run 类）** 才能真正解决问题，因为它们代理包括认证在内的全部 Docker Hub API
4. **配置多个 Mirror 反而有害**：不可达的 mirror 会导致 Docker 快速失败后回退到直连 Docker Hub
5. **NVIDIA NGC（nvcr.io）在中国可达**，可作为基础镜像的来源
6. **Jetson Nano 需要额外的 NVIDIA Runtime 配置**才能让容器访问 GPU
