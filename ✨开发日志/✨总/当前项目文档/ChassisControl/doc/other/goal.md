# 后续工作与演进方向

本文档汇总 `UartToCan_test` 项目在当前稳定版本基础上的**近期验证任务**与**中长期演进规划**。

---

## 1. 近期验证要点

> 代码审查阶段修改已完成（详见 `claude.md`），建议按以下顺序对修改结果进行验证。

| 序号 | 验证项 | 验证方法 | 通过标准 |
| ---- | ------ | -------- | -------- |
| 1 | **环形缓冲区原子性** | 高速连续发送 UART 数据（如 115200 bps 满载） | 无字节丢失，协议解析无错误帧 |
| 2 | **UART 互斥锁** | 同时触发 UART→CAN 发送和 CAN→UART 接收 | 串口输出无乱码交错 |
| 3 | **事件驱动延迟** | 逻辑分析仪测量 UART 字节到达 → CAN 发送的端到端延迟 | 延迟明显低于 1 ms |
| 4 | **任务调度健康度** | 在压力测试期间观察心跳 LED | LED 持续均匀闪烁，无死锁或任务饥饿 |

---

## 2. 中长期演进方向

以下优化按**投入产出比**排序，建议优先实施前两项。

### 2.1 协议功能增强

**CMD 字段扩展**：当前 `CMD` 字节已透传至 CAN 总线，但尚未在网关侧定义控制指令。可扩展如下：

| 指令 | 功能 |
| ---- | ---- |
| `CMD_SET_FILTER` | 通过串口动态修改 CAN 接收过滤器，按需监听特定 ID |
| `CMD_SET_BAUDRATE` | 动态配置 CAN / UART 波特率，无需重新烧录固件 |
| `CMD_QUERY_STATUS` | 查询网关状态（收发计数、错误计数等） |

**应答机制**：为串口指令增加 ACK/NACK 响应。CAN 报文发送成功回复 `ACK`，失败回复 `NACK` 及错误原因码，使主机侧可感知网关执行结果。

---

### 2.2 性能与资源优化

**UART DMA 发送**：`uart1_send()` 已使用 `HAL_UART_Transmit_DMA` + 二进制信号量完成改造（详见 `fix1_UartToDma.md`），CPU 在 DMA 搬运数据期间可被调度出去执行其他任务，显著降低发送阻塞延迟。当前 DMA 缓冲区固定 128 字节，后续可按需评估调整。

**任务栈大小评估**：对各任务运行时栈占用进行水位线检测（`uxTaskGetStackHighWaterMark`），在保证安全裕量的前提下适当收缩，节约宝贵 RAM 资源（STM32F103C8T6 仅有 20 KB SRAM）。

---

### 2.3 健壮性提升

**CAN 总线错误监控**：当前未处理总线关闭（Bus-Off）、错误被动（Error-Passive）等异常状态。建议：
- 监控 `HAL_CAN_GetError()` 返回值。
- 检测到 Bus-Off 时尝试自动恢复（`HAL_CAN_Stop` → `HAL_CAN_Start`）。
- 通过 LED 或串口日志发出明确告警。

**看门狗（Watchdog）**：引入独立看门狗（IWDG），由 `Heartbeat_Ta` 在每次翻转 LED 时同步喂狗。若任意关键任务死锁，心跳停止，看门狗超时后自动复位系统，保障无人值守场景下的设备可靠性。

---

### 2.4 接口扩展

**USB CDC（虚拟串口）**：将 `USART1` 替换为 USB CDC，设备可直接通过 USB 连接 PC，无需外置 USB-TTL 转换器，提升易用性与移植灵活性。

**多路 CAN / UART**：若更换至引脚资源更丰富的 MCU（如 STM32F103RCT6），可扩展为双路 CAN 或双路 UART 的多协议转换网关。
